02 / 执行模型：为什么分两层

脚本负责跑，工作台负责看与定位

工作台是静态页面，发不了 HTTP、读不到数仓。所以「执行」拆成两层：Python runner 真实调用 /api/chat-fc 并收集每条结果 + trace_id；本页 导入它产出的 JSON，做可视化与问题定位。你掌握执行权——跑不跑、跑哪个、什么时候跑，都由你决定。

2层：执行层 + 展示层
1把钥匙：trace_id
2Trace 层 decision / tool_call
8类判定断言
① 发起请求 · 执行层
POST /api/chat-fc {user_id, query}响应含 answer_type 与 trace_id（= turn_id）
② 还原现场 · 定位用
GET /api/trace/{trace_id}decision[] 想调什么 + tool_call[] 实际做了什么

关键：trace_id 是串联一次请求的唯一钥匙。runner 已把它写进每条结果；导入后点开失败 case 就能看到当时的决策轮次、工具名、参数、status、error 与耗时——这是定位问题的必经路径。

参数说明

参数作用什么时候用
--golden指定黄金集文件（jsonl）切换被测集；这是"指定执行哪个黄金集"的落点
--out输出结构化 JSON 路径给本页导入用；每条含 verdict/trace_id/trace 摘要
--report文本报告路径留档；每条行末带 trace_id，末尾有失败 case 定位索引
--id按 case id 筛选（支持前缀）定点复现失败 case，如 --id HP-002
--category按类别筛选专项回归，如只跑越权 adversarial
--limit只跑前 N 条冒烟验证环境是否通
--soft-samples N软断言采样次数（默认 5）提升 tools_must 命中率可信度；更严谨但更慢
--skip-soft跳过软断言采样快速回归；只跑硬断言

已知边界（如实标注，别误判为 bug）：多轮 case 与行为型 case（AM-011~016 上下文隔离等）在当前 FC 链路里无法自动回放——chat_fc 每次只构造 system + 当前问句，不回放 history。这类 case 会被标记或需人工核对，自动化结果不代表它们没测。
