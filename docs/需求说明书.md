## 1. 文档目的与范围

### 1.1 目的

明确取数 Agent 的产品能力边界、功能需求（FR）与非功能需求（NFR），作为研发排期、评测体系搭建与验收的输入。

### 1.2 范围

**In Scope（本期）**
- 卖家侧账号体系与四级角色数据隔离（**不含买家侧**）
- 多轮对话（上下文 + 记忆持久化）与意图澄清
- 指标口径 RAG 及其管理后台
- NL2SQL 取数主流程、结果呈现（表格 + 基础图表）、CSV/Excel 导出
- 只读安全、行/列权限下推、审计合规
- 独立对话页形态（Web），**仅简体中文**

**Out of Scope（本期不做）**
| 项 | 说明 |
| --- | --- |
| 买家侧账号与数据 | 确认无买家侧，账号体系收敛为卖家组织树 |
| 多语言 | 仅简体中文，不做 i18n |
| 系统嵌入 / OpenAPI | 短期做独立对话页，嵌入运营后台与 API 列为长期 |
| 图表下钻联动 / 自定义图表 | F3 锁定为基础图表（折线/柱状/饼） |
| 推送 BI 直连 | 长期目标为推送 IM（企业微信/飞书），本期不做 |
| 底层数仓建模 / 预测算法 / 模型训练 | 不在本说明书范围 |

### 1.3 关键假设

- 后端已存在零售业务数仓，至少覆盖**绩效线 / 物流线 / 零售线**，并提供可用 Schema 与指标口径文档。
- 卖家侧各角色账号体系已具备基础认证（登录态），本 Agent 在其上叠加权限与隔离。
- 数据库仅提供**只读**访问，Agent 不触达写入能力。
- 交互语言固定为**简体中文**，时间与金额口径以中国区业务惯例为准（¥、自然日/周）。

## 2. 术语与角色定义

### 2.1 术语

| 术语 | 说明 |
| --- | --- |
| NL2SQL | 自然语言转 SQL，Agent 的核心引擎能力 |
| 语义层 | 业务指标与物理表/字段的映射层，解耦用户表达与底层结构 |
| 指标口径 | 指标的业务定义与计算规则（如"有效订单量"），通过 RAG 挂载说明 |
| 行级隔离 | 按组织层级过滤数据行，用户仅可见授权范围 |
| 列级权限 | 按角色对敏感字段做隐藏或脱敏 |
| RAG | 检索增强生成，此处用于挂载指标口径、业务规则等说明文档 |

### 2.2 角色与数据隔离层级（卖家侧组织树）

**v1.1 决策：本期无买家侧。** 账号体系仅覆盖卖家侧，按组织树做行级隔离：

```
超级管理员（全部数据）
└── 区域经理（华东 / 华西 / 华南 ……）
    └── 城市经理（单个城市）
        └── 店铺管理员（对应卖家店铺 / 商户）
```

**可见性规则**

- 父节点可**汇总**其下所有子节点数据（区域经理 = 多城市聚合；城市经理 = 多店铺聚合）。
- 子节点**不可越级**看到兄弟节点或父节点授权范围外的数据。
- 店铺管理员（商户）仅见本人/本店数据。
- 所有隔离在 **SQL 层下推**（见 F2），不做"取全量后过滤"。

## 4. 缺口分析：建议补充的产品能力

你列出的 6 项覆盖了**权限、对话、知识、导出**四大块，但作为可上线的企业级取数 Agent，仍缺少"**取数引擎本身、结果呈现、安全兜底、企业特性**"等模块。以下按优先级排序（v1.1 已按决策调整）。

### 4.1 P0 — 核心必备（缺失则无法上线）

| 编号 | 能力 | 为什么必须有 |
| --- | --- | --- |
| F1 | **NL2SQL 核心引擎** | 你列的 6 项默认了"能取数"，但未显式定义引擎：Schema 感知、语义层映射、同义词/别名识别、时间维度解析。这是 Agent 的立身之本。 |
| F2 | **只读安全约束** | 强制 SELECT-only，禁止 DDL/DML；防 SQL 注入；行级权限必须**下推到生成的 SQL**，而非取全量后过滤。 |
| F3 | **查询结果可视化** | 运营与数据分析不只看表。v1.1 锁定为**基础图表**：折线 / 柱状 / 饼，支持数值型结果一键成图；不做图表下钻联动与自定义图表。 |
| F4 | **SQL 透明与可解释** | 展示生成的 SQL、用自然语言解释"问题→SQL"的映射、给出置信度，建立商户与分析师的信任。 |
| F5 | **列级权限与脱敏** | 与 C1 行级隔离互补：PII（手机号、姓名）、成本/毛利等敏感字段按角色隐藏或脱敏。 |
| C6 | **CSV/Excel 导出** | v1.1 锁定为短期交付形态，导出结果与界面一致并附口径脚注。 |

### 4.2 P1 — 重要（显著提升价值）

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| F6 | 查询历史与保存/复用/分享 | 运营高频查询可沉淀为个人/团队查询集。 |
| F7 | 用户反馈与纠错闭环 | 赞/踩、纠正 SQL、把正确写法沉淀到模板或 RAG，持续提升准确率。 |
| F8 | 审计日志 | 记录"谁、何时、查了什么"，满足合规与追溯。 |

## 6. 关键流程

### 6.1 取数主流程

```
用户输入(自然语言, 简体中文)
   → 意图识别 + 业务线判定(绩效/物流/零售)
   → 要素是否齐全? ──否──> 意图澄清(反问)
   → 指标口径 RAG 检索(补全定义)
   → NL2SQL 生成(语义层映射)
   → 权限校验: 行级下推 + 列级脱敏
   → 只读执行
   → 结果呈现(表格 / 基础图表) + SQL 透明
   → CSV/Excel 导出 / 保存 / 下钻 / 反馈
```

### 6.2 多轮会话与记忆

- **短期记忆**：当前会话内的上下文（主体、时间窗、筛选条件）用于指代消解（"那华北呢？"）。
- **长期记忆**：跨会话保留用户偏好、常用业务线、历史查询（留存期见 NFR）。

### 6.3 意图澄清触发条件

- 主体缺失（未指定区域/城市/店铺）；
- 指标歧义（同名不同口径，取 F16 的适用范围标注）；
- 时间范围不清；
- 跨业务线且无法自动判定。

### 6.4 低置信兜底

置信度低于阈值或生成失败 → 返回"暂无法精确回答"，提供相似历史查询或建议转数据团队/运营，禁止猜测性 SQL。

### 6.5 口径维护流程（v1.1 新增）

```
产品/运营 提出口径新增/变更
   → 填写：名称 / 业务定义 / 计算规则 / 排除项 / 示例 / 业务线 / 责任人
   → 冲突检查(是否同名不同口径)
   → 保存并生成新版本
   → 同步至 RAG 索引(明确生效时间)
   → 操作留痕入审计
```

## 7. 非功能需求（NFR）

| 维度 | 要求（示例，需评审定稿） |
| --- | --- |
| 性能 | 首句响应 < 3s；常规查询端到端 < 8s；支持并发 ≥ 50 |
| 安全 | 只读强制；行/列权限下推；传输与存储加密；审计留痕 |
| 合规 | 数据最小化、按角色脱敏、审计留存 ≥ 6 个月 |
| 可用性 | 服务可用 ≥ 99.9%；数仓异常时优雅降级（返回缓存/提示） |
| 可观测 | 全链路日志、查询准确率/澄清率/满意度等评测看板 |
| 可扩展性 | 新增指标/业务线可通过配置 + RAG 文档完成，低代码 |
| **语言** | **仅简体中文（v1.1 锁定），不做多语言** |
| **形态** | **短期独立对话页（Web），预留嵌入/API 接口层** |
