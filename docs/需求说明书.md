## 1. 文档目的与范围

### 1.1 目的

明确取数 Agent 的产品能力边界、功能需求（FR）与非功能需求（NFR），作为研发排期、评测体系搭建与验收的输入。

### 1.2 范围

**In Scope（本期）**
- 卖家侧账号体系与四级角色数据隔离（**不含买家侧**）
- 多轮对话（上下文 + 记忆持久化）与意图澄清
- 指标口径 RAG 及其管理后台
- NL2SQL 取数主流程、结果呈现（表格 + 基础图表）、CSV/Excel 导出
- 只读安全、行/列权限下推、审计合规
- 独立对话页形态（Web），**仅简体中文**

**Out of Scope（本期不做）**
| 项 | 说明 |
| --- | --- |
| 买家侧账号与数据 | 确认无买家侧，账号体系收敛为卖家组织树 |
| 多语言 | 仅简体中文，不做 i18n |
| 系统嵌入 / OpenAPI | 短期做独立对话页，嵌入运营后台与 API 列为长期 |
| 图表下钻联动 / 自定义图表 | F3 锁定为基础图表（折线/柱状/饼） |
| 推送 BI 直连 | 长期目标为推送 IM（企业微信/飞书），本期不做 |
| 底层数仓建模 / 预测算法 / 模型训练 | 不在本说明书范围 |

### 1.3 关键假设

- 后端已存在零售业务数仓，至少覆盖**绩效线 / 物流线 / 零售线**，并提供可用 Schema 与指标口径文档。
- 卖家侧各角色账号体系已具备基础认证（登录态），本 Agent 在其上叠加权限与隔离。
- 数据库仅提供**只读**访问，Agent 不触达写入能力。
- 交互语言固定为**简体中文**，时间与金额口径以中国区业务惯例为准（¥、自然日/周）。

## 2. 术语与角色定义

### 2.1 术语

| 术语 | 说明 |
| --- | --- |
| NL2SQL | 自然语言转 SQL，Agent 的核心引擎能力 |
| 语义层 | 业务指标与物理表/字段的映射层，解耦用户表达与底层结构 |
| 指标口径 | 指标的业务定义与计算规则（如"有效订单量"），通过 RAG 挂载说明 |
| 行级隔离 | 按组织层级过滤数据行，用户仅可见授权范围 |
| 列级权限 | 按角色对敏感字段做隐藏或脱敏 |
| RAG | 检索增强生成，此处用于挂载指标口径、业务规则等说明文档 |

### 2.2 角色与数据隔离层级（卖家侧组织树）

**v1.1 决策：本期无买家侧。** 账号体系仅覆盖卖家侧，按组织树做行级隔离：

```
超级管理员（全部数据）
└── 区域经理（华东 / 华西 / 华南 ……）
    └── 城市经理（单个城市）
        └── 店铺管理员（对应卖家店铺 / 商户）
```

**可见性规则**

- 父节点可**汇总**其下所有子节点数据（区域经理 = 多城市聚合；城市经理 = 多店铺聚合）。
- 子节点**不可越级**看到兄弟节点或父节点授权范围外的数据。
- 店铺管理员（商户）仅见本人/本店数据。
- 所有隔离在 **SQL 层下推**（见 F2），不做"取全量后过滤"。

## 4. 缺口分析：建议补充的产品能力

你列出的 6 项覆盖了**权限、对话、知识、导出**四大块，但作为可上线的企业级取数 Agent，仍缺少"**取数引擎本身、结果呈现、安全兜底、企业特性**"等模块。以下按优先级排序（v1.1 已按决策调整）。

### 4.1 P0 — 核心必备（缺失则无法上线）

| 编号 | 能力 | 为什么必须有 |
| --- | --- | --- |
| F1 | **NL2SQL 核心引擎** | 你列的 6 项默认了"能取数"，但未显式定义引擎：Schema 感知、语义层映射、同义词/别名识别、时间维度解析。这是 Agent 的立身之本。 |
| F2 | **只读安全约束** | 强制 SELECT-only，禁止 DDL/DML；防 SQL 注入；行级权限必须**下推到生成的 SQL**，而非取全量后过滤。 |
| F3 | **查询结果可视化** | 运营与数据分析不只看表。v1.1 锁定为**基础图表**：折线 / 柱状 / 饼，支持数值型结果一键成图；不做图表下钻联动与自定义图表。 |
| F4 | **SQL 透明与可解释** | 展示生成的 SQL、用自然语言解释"问题→SQL"的映射、给出置信度，建立商户与分析师的信任。 |
| F5 | **列级权限与脱敏** | 与 C1 行级隔离互补：PII（手机号、姓名）、成本/毛利等敏感字段按角色隐藏或脱敏。 |
| C6 | **CSV/Excel 导出** | v1.1 锁定为短期交付形态，导出结果与界面一致并附口径脚注。 |

## 6. 关键流程

### 6.1 取数主流程

```
用户输入(自然语言, 简体中文)
   → 意图识别 + 业务线判定(绩效/物流/零售)
   → 要素是否齐全? ──否──> 意图澄清(反问)
   → 指标口径 RAG 检索(补全定义)
   → NL2SQL 生成(语义层映射)
   → 权限校验: 行级下推 + 列级脱敏
   → 只读执行
   → 结果呈现(表格 / 基础图表) + SQL 透明
   → CSV/Excel 导出 / 保存 / 下钻 / 反馈
```

### 6.2 多轮会话与记忆

- **短期记忆**：当前会话内的上下文（主体、时间窗、筛选条件）用于指代消解（"那华北呢？"）。
- **长期记忆**：跨会话保留用户偏好、常用业务线、历史查询（留存期见 NFR）。

### 6.3 意图澄清触发条件

- 主体缺失（未指定区域/城市/店铺）；
- 指标歧义（同名不同口径，取 F16 的适用范围标注）；
- 时间范围不清；
- 跨业务线且无法自动判定。

### 6.4 低置信兜底

置信度低于阈值或生成失败 → 返回"暂无法精确回答"，提供相似历史查询或建议转数据团队/运营，禁止猜测性 SQL。

### 6.5 口径维护流程（v1.1 新增）

```
产品/运营 提出口径新增/变更
   → 填写：名称 / 业务定义 / 计算规则 / 排除项 / 示例 / 业务线 / 责任人
   → 冲突检查(是否同名不同口径)
   → 保存并生成新版本
   → 同步至 RAG 索引(明确生效时间)
   → 操作留痕入审计
```

## 9. Agent 能力契约（Capability Spec）

> 完整版见 [Agent能力契约.md](Agent能力契约.md)。本节内嵌核心契约，是安全与行为边界测试断言的源头。

**业务目标**：在只读、权限隔离、口径一致的前提下，把自然语言问句转成可信可追溯的数据结果。任何偏离（写操作、越权、编造、静默猜测）都是契约违约。

### 9.1 MUST — 必须做

| # | 义务 | 判定标准 | 代码落点 |
| --- | --- | --- | --- |
| M1 | 只读取数 | 生成 SQL 必为单条 SELECT | `validator.validate` |
| M2 | 行级隔离 | 权限条件注入 SQL 的 WHERE，参数化 | `permission.row_filter_clause` |
| M3 | 列级脱敏 | 禁用列剔除、敏感列按模板脱敏 | `permission.denied_columns/mask_expression` |
| M4 | 口径一致 | 指标按语义层 expr 编译，附口径引用 | `semantic_layer.yaml` / `caliber_refs` |
| M5 | SQL 透明 | result 态返回 SQL 与映射说明 | `ChatResponse.sql/explanation` |
| M6 | 结果可追溯 | 每请求生成 trace_id，记录决策与执行 | `trace.new_turn/decision/tool_call` |
| M7 | 歧义必澄清 | 同名不同口径/缺主体/时间不清时反问 | `answer_type=clarify` |
| M8 | 低置信兜底 | 置信度 < 0.60 转 fallback，不硬编 SQL | `intent.min_confidence` |
| M9 | 后置工具依赖检查 | 导出/下钻前必须有 query_metrics 结果 | `dispatcher.export_result/drilldown_detail` |
| M10 | 审计留痕 | 查询/导出/下钻/口径变更均记录 | `audit.log` |
| M11 | 多轮记忆隔离 | 会话槽内继承槽位，跨会话不串数据 | `session_store` |
| M12 | 工具参数校验 | 每次工具调用先过 Schema 校验再执行 | `tool_schemas.validate_call` |

### 9.2 MUST NOT — 禁止做（红线）

| # | 禁止行为 | 防线 |
| --- | --- | --- |
| N1 | 禁止写操作（INSERT/UPDATE/DELETE/DDL） | validator 黑名单 + 只读库 |
| N2 | 禁止注入（多语句、注释、参数夹带控制字符） | validator `_FORBIDDEN`/`_COMMENT` |
| N3 | 禁止非白名单表/子查询 | validator 视图白名单 |
| N4 | 禁止越权（放大可见范围、泄露禁用列） | 权限下推 + 列策略 |
| N5 | 禁止编造指标 id | intent 白名单 + 工具 enum 校验 |
| N6 | 禁止猜测 SQL | 无法确定时走 fallback |
| N7 | 禁止编造工具参数 | `validate_call` → `extra_arg` |
| N8 | 禁止跨 turn 串上下文 | `_TURN_CTX` 按 turn_id 隔离 |
| N9 | 禁止泄露内部信息（堆栈/密钥/路径） | error 态仅回原因文本 |
| N10 | 禁止用反问替代工具调用（chat-fc 链路） | system prompt + 日期锚点 |

### 9.3 ESCALATE — 需人工审批/升级边界

| 场景 | 触发条件 | 响应态 |
| --- | --- | --- |
| 指标歧义 | "销售额"同时命中 retail/pay_amount 与 performance/perf_gmv | `clarify` |
| 必要槽位缺失 | 无指标、主体缺失、时间完全不清 | `clarify` |
| 低置信 | confidence < 0.60 | `fallback` |
| 无法生成 | 三轮工具决策仍未拿到数据 | `fallback` |
| 权限拒绝 | 账号未知/指标依赖禁用字段 | `error` |
| Provider 不支持 | 无 function calling 能力 | `error` |
| 口径变更 | 产品/运营修改口径文档 | 需重建 RAG 索引后生效 |

### 9.4 禁止动作清单（不可逆操作/写权限）

`validator._FORBIDDEN` 显式拦截的关键字（缺陷开关 D08 关闭时生效）：

```
INSERT UPDATE DELETE DROP ALTER CREATE TRUNCATE REPLACE
ATTACH DETACH PRAGMA VACUUM EXEC EXECUTE REINDEX LOAD_EXTENSION
```

同时禁止：多语句 `;`（D07）、SQL 注释 `-- /* */ #`（D07）、子查询 `FROM (`、非白名单表引用。
**写权限**：Agent 对业务数仓全程只读（`readonly=true`）；产品/运营仅可改口径文档（元数据，可回滚），用户仅可写反馈记录，均不涉及业务数据写入。本项目无不可逆的用户侧动作。

### 10.3 四态响应语义

| 状态 | 触发 | 允许 | 禁止 |
| --- | --- | --- | --- |
| `result` | 成功取数 | 返回 sql/rows/图表/凭证 | 不得夹带越权列 |

### 10.4 可量化验收标准（业务正确性断言源）

| 编号 | 验收项 | 判定标准 |
| --- | --- | --- |
| A1 | 主链路可用 | 有数据时间窗 → result 且 row_count>0、sql 含正确视图 |
| A2 | 业务线正确 | 物流命中 `v_logistics_ship`，绩效命中 `v_performance` |
| A3 | 日期换算 | "近7日"=含今日 7 天（date_start=今日-6） |
| A4 | 指标口径 | 有效订单量含 `is_valid=1`；客单价分母为有效单量 |
| A5 | 聚合正确 | SUM/AVG/MAX/MIN 结果等于独立 oracle 真值 |
| A6 | 行级隔离 | 四角色查询不越权 |
| A7 | 列级脱敏 | 非授权角色无禁用列、手机号脱敏 |
| A8 | 歧义澄清 | "销售额"触发 clarify |
| A9 | 缺失兜底 | 不存在指标/无前置上下文不受理并给 suggestions |
| A10 | 只读安全 | 注入/写操作输入被 validator 拦截 |
| A11 | 审计完整 | 查询/导出/下钻/口径变更均有记录 |
| A12 | 结果可追溯 | 每个 result 带 trace_id，可捞 decision + tool_call |

## 11. Agent 架构与编排设计

> 完整版见 [Agent架构与编排设计.md](Agent架构与编排设计.md)。

### 11.1 双链路编排

| 维度 | 链路 A：`chat()` 规则编排 | 链路 B：`chat_fc()` 模型驱动 |
| --- | --- | --- |
| 决策者 | Python 写死流水线 | LLM 选工具 + 填参数 |
| 流程 | build_plan→RAG→compile→run→呈现 | 决策→执行→回填→再决策（循环） |
| 确定性 | 高（同输入同输出） | 有随机性（temperature=0 降低） |
| 端点 | `/api/chat` | `/api/chat-fc` |
| 打点 | audit + metrics | audit + metrics + **双层 trace** |

`QueryPlan`（`models.py`）是枢纽契约：理解侧只产出 Plan，执行侧只消费 Plan，LLM 不直接写 SQL。

### 11.2 状态机与循环终止

请求级状态机：`INIT → DECIDE → EXECUTE → FEEDBACK →（未终止则回 DECIDE）→ FINALIZE`。
响应态状态机：`result`（完成）/`clarify`、`fallback`（可恢复，用户补充后带 session_id 重入）/`error`（终止）。

模型驱动循环终止条件：

| 条件 | 触发 | 后续 |
| --- | --- | --- |
| ① 调用失败 | `complete_with_tools` 返回 None | 跳出，last_result 空 → fallback |
| ② 模型停止 | tool_calls 为空 / finish=stop | 正常跳出 → result/fallback |
| ③ 轮次超限 | 达 `MAX_ROUNDS=3` | 记 `tool_round_limit` → FINALIZE |
| ④ 权限拒绝 | load_user 抛异常 | 直接 error |

### 11.3 防死循环策略

硬轮次上限 3；超限指标 `tool_round_limit`；tool 结果摘要化防上下文膨胀；后置工具无前置直接 error；temperature=0；assistant.tool_calls 带 id 原样回填避免协议错位。

### 11.4 三层记忆

| 层级 | 载体 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| 短期会话槽 | `session_store` | ttl=60min，max 10 轮 | 指代消解（"那华东呢？"） |
| 长期记忆 | `long_term.py`（JSON 落盘） | 跨会话 | 偏好、历史查询、反馈纠错 |
| turn 级上下文 | `dispatcher._TURN_CTX` | 单次请求 | 取数结果→导出/下钻 |

### 11.5 双层 Trace 与 Agent 指标

| kind | 记录方 | 关键字段 |
| --- | --- | --- |
| `decision` | `chat_fc` 每轮 | `round`/`selected`/`raw`/`finish_reason` |
| `tool_call` | `dispatcher.execute` 每次 | `tool_name`/`tool_args`/`tool_return`(摘要)/`status`/`latency_ms`/`error` |

`decision` 回答"模型选对没"，`tool_call` 回答"执行对没"。从 trace 计算：工具调用正确率=`selected` vs 期望集合；参数正确率=tool_args 过 Schema；无效调用占比=`status∈{empty,error}`；冗余调用=相同签名重复；缺失调用=期望集合差；平均轮次=每次 decision 条数均值；超限占比=达 MAX_ROUNDS 请求比例。

## 12. Tools（Function Calling）规范

> 完整版见 [Tools函数文档.md](Tools函数文档.md)。事实来源 `tool_schemas.py` / `dispatcher.py`。

### 12.1 七个能力工具（按能力种类拆分，非按业务线）

| # | 工具 | 类别 | 状态性 | 依赖 | 用途 |
| --- | --- | --- | --- | --- | --- |
| T1 | `query_metrics` | 主取数 | 无状态（写 ctx） | 无 | 按业务线/指标/维度取聚合数据 |
| T2 | `search_caliber` | 知识 | 无状态 | 无 | 检索口径文档 |
| T3 | `compare_period` | 分析 | 无状态 | 无 | 周期对比（当前回执实现） |
| T4 | `get_data_dictionary` | 知识 | 无状态 | 无 | 查指标/维度/业务线清单 |
| T5 | `export_result` | 交付 | **有状态** | 需 T1 成功 | 导出 CSV/Excel |
| T6 | `drilldown_detail` | 分析 | **有状态** | 需 T1 成功 | 展开明细 |
| T7 | `query_history` | 效率 | 无状态（读外部状态） | 无 | 查历史问句 |

> 判据：同样参数两次调用，结果是否依赖参数外的隐藏状态。T5/T6 读 `_TURN_CTX`（参数外）→ 真有状态；`business_line` 是 T1 的参数，不是独立工具。

### 12.2 核心工具 Schema

**T1 `query_metrics`**（主取数）：

| 参数 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `business_line` | string | ✅ | enum：`retail`/`logistics`/`performance` |
| `metrics` | array[string] | ✅ | items enum：语义层 13 个 metric id |
| `dimensions` | array[string] | ❌ | items enum：7 个 dimension id |
| `date_start`/`date_end` | string | ✅ | pattern `^\d{4}-\d{2}-\d{2}$` |

枚举从配置**动态生成**（业务线取 `business_lines.yaml`，指标/维度取 `semantic_layer.yaml`），不硬编码。出参摘要：`{row_count, columns, rows[:5], sql, view}`；成功且有行时写 `_TURN_CTX.last_result/last_plan/last_meta`。

其余工具入参：`search_caliber(query, business_line?)`、`compare_period(business_line, compare_type∈{mom,yoy,dod})`、`get_data_dictionary(business_line?)`、`export_result(fmt∈{csv,xlsx})`、`drilldown_detail(reason?)`、`query_history(limit?)`。

### 12.3 统一执行契约与错误码

所有调用必经 `dispatcher.execute()`：`校验(validate_call) → 执行(handler) → 打点(trace) → 返回`。
**不抛异常**，失败转成 `status=error` 写入 trace。返回固定三字段：`{status, error, result}`，status ∈ `ok`/`empty`/`error`。

| 错误码（`validate_call`） | 含义 | 示例 |
| --- | --- | --- |
| `unknown_tool:{name}` | 工具未注册 | 编造工具名 |
| `missing:{k}` | 缺必填参数 | 缺 date_start |
| `extra_arg:{k}` | 多余参数 | 传未定义的 bad |
| `enum:{k}={v}` | 枚举非法 | business_line=warehouse |
| `pattern:{k}={v}` | 正则不匹配 | date_start=11/01 |
| `type:{k}` | 类型错误 | limit 传字符串 |

### 12.4 调用约束 / 幂等 / 超时

- **依赖链**：T5/T6 必须在 T1 成功后调用（ctx 已写），否则 error；ctx 按 turn_id 隔离，跨 turn 不继承。
- **幂等**：T1/T2/T3/T4/T7 幂等（只读）；T5/T6 每次生成新 token（非幂等，内容一致）。
- **超时**：`complete_json` 20s、`complete_with_tools` 30s、导出上限 50000 行、会话 TTL 60min/10 轮。
- **重试**：无代码层自动重试；工具失败把 error 回填给模型，由模型决定是否换参重试（受 MAX_ROUNDS 限制）。

## 14. Guardrail 安全规则

> 完整版见 [Guardrail安全规则文档.md](Guardrail安全规则文档.md)。

### 14.1 纵深防御（每层独立，不共享假设）

`L1 输入过滤(Schema) → L2 意图约束(Prompt+白名单) → L3 SQL 编译(确定性) → L4 执行前校验(validator) → L5 权限与脱敏(SQL 层) → L6 输出审核(响应态+审计+trace)`

越靠近数据的防线越独立：L4 不信任 L3 的编译结果；L5 不信任应用层过滤（聚合指标事后过滤不成立，越权数据一旦进内存即从日志/异常泄露）。

### 14.2 注入防护（L4，`validator.validate`）

| 检查 | 规则 | 缺陷开关 |
| --- | --- | --- |
| 单条 SELECT | 必须以 SELECT 开头 | — |
| DDL/DML 关键字 | 18 个关键字黑名单 | D08（关闭时跳过） |
| 多语句 | 禁止 `;` | D07（关闭时跳过） |
| SQL 注释 | 禁止 `--` `/*` `#` | D07（关闭时跳过） |
| 子查询 | 禁止 `FROM (` | — |
| 表白名单 | FROM/JOIN 须为业务线视图 | — |
| 参数控制字符 | 禁止 `'` `"` `;` `--` `/*` | — |

### 14.3 敏感信息拦截（L5）

| scope | 行级下推条件 |
| --- | --- |
| `all` | `1=1` |
| `region` | `region_name = ?` |
| `city` | `city_name = ?` |
| `store` | `store_id = ?` |

列策略：`full`（超管，无限制）/ `standard`（区域/城市经理，禁 cost_amount、supplier_cost，手机号脱敏）/ `restricted`（店长，再加禁 commission、target_gmv）。脱敏模板：手机号 `138****5678`，金额分转元取整。缺陷开关 D03（区域下推缺失）、D04（下钻未收窄）、D05（脱敏失效）、D06（禁用列失效）、D16（导出未绑账号）。

### 14.4 输出审核与拒绝话术

| 场景 | 态 | 规范话术 |
| --- | --- | --- |
| 指标歧义 | clarify | "「销售额」在不同业务线下口径不同，你想看哪一个？" |
| 低置信/无法确定 | fallback | "这次没能确定业务线和指标，请补充（如'零售线近7日各城市有效订单量'）" |
| 未知账号 | error | "未知账号: {user_id}" |
| 指标越权 | error | "指标「X」依赖的字段 [...] 不在你的可见范围内" |
| 无前置导出 | error | "没有可导出的结果，请先调用 query_metrics" |

话术原则：说明原因、给出下一步、不暴露内部细节、简体中文。
