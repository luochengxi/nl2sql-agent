## 2. 数据是怎么造出来的（原理 → 为什么 → 好处）

| 设计 | 原理 | 为什么 | 好处 |
| --- | --- | --- | --- |
| 固定随机种子 `SEED=20261103` | `random.Random(SEED)` | 随机数不确定 → 断言会飘 | 每次生成逐行一致，可写精确期望值 |
| `--today` 可注入锚定日 T | 所有日期由 T 反推 | 依赖真实日历的测试「昨天能过今天挂」 | 时间窗口断言可复现 |
| **数据只生成到 T-1** | `range(days, 0, -1)` | 与口径文档「近7日不含当天」一致；否则当天数据虚低 | 口径与数据自洽，不会出现「今天暴跌」的假象 |
| 组织树从 `org_tree.yaml` 读 | 灌数与意图识别共用同一份配置 | 避免「库里有这个城市、意图层却不认识」 | 单一数据源，无漂移 |
| `is_valid` / `is_signed` / `is_ontime` 标记列 | 把业务口径预计算成 0/1 标记 | 让口径能用 SQL 精确表达，而不是让模型猜 | 口径可断言、可审计 |
| 三张宽表视图固化 JOIN | 视图里 JOIN 好维度表 | 编译器只面向单表，行级权限有唯一注入点 | 不让 LLM 猜 JOIN、隔离不会被绕过 |
| 周末效应 `weekend_boost=1.4` | 周六日单量放大 | 让趋势图有形状 | 可视化与同比环比有可观察的波动 |

## 3. 数仓结构

### 3.1 对象清单与规模

```
维度表（5）          行数
  dim_region            4       R01华东 / R02华西 / R03华南 / R04华北
  dim_city              9       4 区域下共 9 城市
  dim_store            18      每城市 2 店（S001..S018）
  dim_seller           18      1 店 1 卖家（SL001..SL018）
  dim_product          12      4 品类（服饰/食品/数码/日化），每类 3 个商品

事实表（3）          行数      日期范围
  fact_order         15281    2026-07-06 ~ 2026-11-02
  fact_logistics     12779    同上
  fact_performance    2160    同上（每店每天 1 条 = 18 × 120）

宽表视图（3）
  v_retail_order       零售线
  v_logistics_ship     物流线
  v_performance        绩效线
```

### 3.2 三层结构

```
dim_*（维度：区域/城市/店铺/卖家/商品）
   │  JOIN
fact_*（事实：订单/物流/绩效，带度量与状态标记）
   │  固化为
v_*（宽表视图：Agent 唯一允许查询的对象）
```

**关键约束**：`validator.py` 只允许查询这三个视图，不允许直接查 `fact_*` / `dim_*`。
三个视图都**统一携带同一套权限列**（`region_name` / `city_name` / `store_id` / `seller_phone` / `cost_amount` / `commission` / `target_gmv`），因此行级过滤与列级脱敏逻辑对三条业务线完全一致。

## 4. 字段字典

### 4.1 `fact_order`（零售线事实表）

| 字段 | 类型 | 业务含义 / 取值 | 支撑的需求 |
| --- | --- | --- | --- |
| `order_id` | TEXT PK | 订单号 `O0000001`… | F10 下钻明细的主键 |
| `order_date` | TEXT | 下单日期（自然日 `YYYY-MM-DD`） | F1 时间解析、F9 同比环比、C5「近7日」 |
| `store_id` / `seller_id` | TEXT | 店铺 / 卖家外键 | **C1/F2 行级隔离**（store 级下推） |
| `product_id` | TEXT | 商品外键 | F1 品类/商品维度 |
| `qty` | INT | 购买件数 1–4 | F1「销量」指标 |
| `order_amount` | REAL | 订单应付金额 | 辅助字段 |
| `pay_amount` | REAL | **实付金额**；已取消订单 = 0 | C5「销售额」口径、F1 客单价 |
| `cost_amount` | REAL | 成本（敏感） | **F5 列级权限**：standard/restricted 角色 deny |
| `order_status` | TEXT | 已完成 / 已取消 / 已退款 / 待发货 | C5「有效订单量」「订单量」「退款率」 |
| `is_valid` | INT | 1 = 已完成；其余 = 0 | **C5 有效订单量口径的落地字段** |
| `customer_phone` | TEXT | 买家手机号（PII） | **F5 脱敏**：standard/restricted 角色 mask |

状态分布（全库，固定值）：

| order_status | 行数 | is_valid |
| --- | --- | --- |
| 已完成 | 11898 | 1 |
| 已取消 | 1372 | 0 |
| 已退款 | 1221 | 0 |
| 待发货 | 790 | 0 |
| **合计** | **15281** | **11898** |

> 注意口径差异：`销售额 = SUM(pay_amount)` **含已退款**；`有效订单量` 只数 `已完成`。
> 两者分母不同，不能直接相除得到客单价 —— 这正是口径文档《销售额》里标注的「常见误解」。

### 4.2 `fact_logistics`（物流线事实表）

| 字段 | 业务含义 | 支撑的需求 |
| --- | --- | --- |
| `shipment_id` / `ship_date` | 运单号 / 发货日期（业务线时间列） | F11 业务线切换、F1 时间解析 |
| `order_id` | 关联订单 | 跨主题下钻 |
| `is_same_city` | 是否同城（决定 24h / 48h 承诺时效） | C5「及时妥投率」 |
| `is_signed` | 是否签收 | C5「及时妥投率」分母、「履约时效」分母 |
| `delivery_hours` | 履约耗时（小时）；未签收为 NULL | C5「履约时效」 |
| `is_ontime` | 是否在承诺时效内；未签收为 NULL | C5「及时妥投率」分子 |
| `supplier_cost` | 供应商成本（敏感） | F5 列级 deny |
| `store_id` | 店铺外键 | C1/F2 行级隔离 |

### 4.3 `fact_performance`（绩效线事实表）

| 字段 | 业务含义 | 支撑的需求 |
| --- | --- | --- |
| `stat_date` | 统计日期（业务线时间列） | F1/F9 |
| `gmv` | 实际 GMV（绩效口径） | F1「绩效销售额」；**与零售线「销售额」同名不同口径 → C3 意图澄清** |
| `target_gmv` | 目标 GMV（敏感） | C5「目标达成率」分母、F5 store_admin deny |
| `commission` | 佣金（敏感） | F5 store_admin deny |
| `store_id` / `seller_id` | 隔离键 | C1/F2 |

### 4.4 视图里的「空列」

三个视图都把不属于自己主题的字段补成 `NULL`（例如 `v_retail_order` 里 `gmv = NULL`）。
**为什么**：让三条业务线共享同一套列级权限规则与下钻列配置，不必按视图写三套分支代码。

## 6. 口径 → 字段 → SQL 表达式 对照（9 篇文档）

| 口径文档 | 版本 / 维护方 | 依赖字段 | 语义层中的 `expr` | 对应需求 |
| --- | --- | --- | --- | --- |
| `有效订单量.md` | 1.2 / 产品-零售组 | `is_valid` | `SUM(CASE WHEN is_valid=1 THEN 1 ELSE 0 END)` | C5、F1 |
| `订单量.md` | 1.0 / 产品-零售组 | 全部行 | `COUNT(*)` | C5（与有效订单量的对比） |
| `销售额.md` | 1.1 / 产品-零售组 | `pay_amount` | `ROUND(SUM(pay_amount),2)` | C3 歧义、C5 |
| `客单价.md` | 1.0 / 产品-零售组 | `pay_amount`、`is_valid` | `SUM(pay_amount)/NULLIF(有效订单量,0)` | C5 |
| `近7日.md` | 1.3 / 运营-数据组 | `order_date` 等业务线时间列 | `[T-7, T-1]`，**不含当天** | C5、F9 |
| `履约时效.md` | 1.1 / 运营-物流组 | `delivery_hours`、`is_signed` | `ROUND(AVG(delivery_hours),1)` | C5、F11 |
| `及时妥投率.md` | 1.2 / 运营-物流组 | `is_signed`、`is_ontime` | 及时签收 / 已签收 | C5、F11 |
| `目标达成率.md` | 1.0 / 运营-经营分析组 | `gmv`、`target_gmv` | `SUM(gmv)/NULLIF(SUM(target_gmv),0)` | C5、F11 |
| `同比环比.md` | 1.0 / 运营-数据组 | 时间列 | 对比周期平移 | F9 |

> **口径文档与语义层是两回事，别混淆**：
> 口径文档是给人和 RAG 看的**业务定义**（为什么这么算、边界是什么）；
> 语义层 `expr` 是给编译器看的**物理实现**（怎么算出这个数）。
> 二者一致性本身就是一条值得验证的需求（改了文档却没改 expr，或 RAG 索引没刷新）。

## 8. ⚠️ 一个必须先处理的问题：时间基准会漂移

**现象**：`config/settings.yaml` 里 `time.today: null`（取系统当天）。

- 数仓是当初用 `--today 2026-11-03` 生成的，数据**只到 2026-11-02**；
- 而系统当前日期已经是 **2026-11-06**；
- 于是「近7日」被解析成 `2026-10-30 ~ 2026-11-05`，其中只有 4 天有数据；
- 实测同一问句「近7日各城市有效订单量」的上海值从 **86 变成 47**，行数仍是 9 行 —— **结果"看起来正常"但数值是错的**。

**为什么这是个坑**：它不会报错、不会空结果，只会静默给出偏小的数字。如果直接拿它写断言，测试会在换一天后失败，或者更糟——断言锁死了一个错误的值。

**两种修法，都需要你自己动手改一次**（改完 `settings()` 有 lru_cache，需重启服务）：

**修法 A（推荐，适合做测试）**：把 T 钉死，与数仓对齐
```yaml
# config/settings.yaml
time:
  today: "2026-11-03"     # null -> 固定日期
  default_window_days: 7
```

**修法 B（适合想按真实日期演示）**：把数仓重建到今天
```bash
./.venv/bin/python scripts/init_warehouse.py --today $(date +%F) --days 120
```
但注意：这样每次重建数据都不同，测试期望值就不能写死，得用「相对断言」。

> 技术方案拆解 §「时间基准 T 可注入」讲的就是这个设计：T 可注入是**能力**，但默认值必须显式钉死，能力才真正发挥出来。这一条本身就值得你作为一个测试关注点。

## 9. 自己查数据的命令（动手实践用）

```bash
cd /Users/andrew/WorkBuddy/2026-11-03-15-44-09/nl2sql-agent

# 看有哪些表/视图
sqlite3 data/warehouse.db ".tables"
sqlite3 data/warehouse.db "PRAGMA table_info(v_retail_order);"

# 看视图定义（理解 JOIN 固化在哪）
sqlite3 data/warehouse.db "SELECT sql FROM sqlite_master WHERE name='v_retail_order';"

# 直接查数（这是"正确答案"的来源，不经过 Agent）
sqlite3 -header -column data/warehouse.db \
  "SELECT city_name, SUM(is_valid) FROM v_retail_order
   WHERE order_date BETWEEN '2026-10-27' AND '2026-11-02'
   GROUP BY city_name ORDER BY city_name;"

# 看 Agent 实际生成的 SQL（对比上面手写 SQL）
curl -s -X POST http://127.0.0.1:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"U002","query":"近7日各城市有效订单量"}' | python3 -m json.tool
```

**取「标准答案」的思路**：先用手写 SQL 从视图算出期望值，再让 Agent 回答同一问句，比对结果。这样期望值不依赖 Agent 自己的输出，断言才有意义。

## 10. 数据里可用于构造断言的确定性事实

以下都是**数据事实**，不是测试用例设计，供你自行取用：

- 组织规模：4 区域 / 9 城市 / 18 店铺 / 18 卖家 / 12 商品 / 4 品类。
- 日期范围：`2026-07-06 ~ 2026-11-02`，共 120 天，止于 T-1。
