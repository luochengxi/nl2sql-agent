# 黄金测试用例集（Golden Dataset）说明

> 文档版本：v1.0　更新日期：2026-11-19
> 交付物：`tests/golden/golden_cases.jsonl`（主）、`golden_cases.yaml`（同源可读版）、`build_golden.py`（构建器）
> 规模：**61 条**（happy_path 27 / multi_turn 4 / tool_chain 5 / parallel 2 / boundary 5 / anomaly 9 / adversarial 9）
> 定位：Agent 评测的**预期基准数据**。测试运行时只读、不重算；用来回答"这次改动让哪类能力退化"。

---

## 1. 两个关键点先讲清

### 1.1 黄金值是"冻结"的，不是运行时算的

`build_golden.py` 在**生成时**用独立 SQL 从数仓算出 `rows_exact`，写进文件后就**冻结**。测试运行时：
- ❌ 不调用被测 Agent 的语义层 / 编译器去算预期（那是同源，测不出口径漂移）
- ✅ 直接拿文件里的冻结值跟 Agent 返回值比

这保证预期与被测**解耦**——哪天有人改了 `semantic_layer.yaml` 的表达式，Agent 结果会变，但黄金集不变，测试立刻报红。这就是"独立 oracle"的意义。

黄金值不是写死的常量表——要重建就跑一次构建器（数据变了、口径正式变更时）：

```bash
.venv/bin/python tests/golden/build_golden.py
```

### 1.2 时间锚点固定 T = 2026-11-03

数仓数据窗口是 `2026-07-06 ~ 2026-11-02`。测试环境必须把 `settings()["time"]["today"]` 冻结为 `ANCHOR_T=2026-11-03`（`tests/conftest.py` 已做），否则"近7日"随真实日期漂移、黄金值对不上。

| 时间短语 | 计算口径 | 实际窗口 |
| --- | --- | --- |
| 近7日 | `[T-7, T-1]` | 2026-10-27 ~ 2026-11-02 |
| 近30日 | `[T-30, T-1]` | 2026-10-04 ~ 2026-11-02 |
| 昨日 | `T-1` 单日 | 2026-11-02 |
| 2026-12-01到2026-12-07 | 显式 | 数仓无覆盖 → 合法空结果 |

> 口径与 `tests/query_spec.py` 的 `relative()` 一致。注意"近7日 = 含今天向前7天"还是"[T-7,T-1]"是需求决策；本项目锁定后者（T 是业务今日，昨日才有完整数据），BD-003 就是这条口径的守卫用例。

## 2. 用例字段 Schema

每行（JSONL）是一个 JSON 对象，字段如下。YAML 版字段完全相同，只是便于人读和 diff。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | 唯一编号，前缀表类别：`HP`/`MT`/`TC`/`PA`/`BD`/`AN`/`AD` |
| `category` | enum | `happy_path` / `multi_turn` / `tool_chain` / `parallel` / `boundary` / `anomaly` / `adversarial` |
| `difficulty` | enum | `easy` / `medium` / `hard` |
| `query` | string | 用户输入原话；多轮用例里是**本轮**输入 |
| `context` | object | 见下表 |
| `expected_action` | enum | `result` / `clarify` / `fallback` / `error`（对应 `ChatResponse.answer_type`） |
| `expected_tools` | array | 预期工具调用序列，见下表 |
| `verdict` | object | 判定标准，见下表 |
| `tags` | array[string] | 多维标签，用于按域筛选回归集合 |

### 2.1 `context`

| 字段 | 含义 |
| --- | --- |
| `user_id` | 演示账号 U001–U007；U999=未知账号 |
| `anchor_t` | 冻结的今日 2026-11-03 |
| `session_id` | 多轮用例的会话 id；单轮为 null |
| `turn_index` | 第几轮 |
| `history` | 历史轮次摘要（query / answer_type / 上轮槽位） |
| `provider` | `openai_like`（真实）/ `unavailable`（注入故障）/ `whitebox_dispatcher`（白盒直驱） |
| `defect_mode` | 该用例关联的缺陷开关（当前留空，变异检测时用） |

### 2.2 `expected_tools[]`

| 字段 | 含义 |
| --- | --- |
| `name` | 工具名，取自 7 个注册工具 |
| `args_contract` | 关键入参的期望约束（业务线/指标/维度/日期/筛选） |
| `required` | 是否必须出现 |
| `order` | 期望顺序（工具链用） |
| `parallel_group` | 同组表示应在同一轮并行调用 |
| `depends_on` | 前置依赖工具（后置工具须在其之后） |

### 2.3 `verdict`（判定标准）

| 字段 | 判定方式 | 说明 |
| --- | --- | --- |
| `answer_type` | 硬断言 | `resp.answer_type` 必须等于此值 |
| `sql_must` | 硬断言 | SQL 文本必须包含（表名、列、过滤条件、脱敏表达式） |
| `sql_must_not` | 硬断言 | SQL 不得包含（DDL/DML/注入片段/非白名单表） |
| `rows_exact` | 硬断言 | 冻结的黄金结果值；`null`=本例不验值 |
| `row_count` | 硬断言 | 期望行数；`null`=不验 |
| `tools_must` | 软断言 | trace 的 decision 里应出现的工具集合 |
| `tools_must_not` | 硬断言 | 不得出现的工具 |
| `no_tool_status` | 硬断言 | tool_call 不得出现的状态（如 `error`） |
| `forbidden_text` | 硬断言 | 响应文本不得泄露的内容（system prompt/堆栈/密钥） |
| `note` | — | 设计意图、对应缺陷靶点 |

## 3. 覆盖矩阵

### 3.1 正向用例（HP-001 ~ HP-027）正交覆盖

| 覆盖维度 | 取值 | 用例保证 |
| --- | --- | --- |
| 指标（13 个） | valid_order_cnt / order_cnt / pay_amount / aov / refund_rate / sales_qty / shipment_cnt / avg_delivery_hours / ontime_rate / perf_gmv / achieve_rate / commission / target_gmv | 每个指标至少 1 条正向 |
| 维度（7 个配置维度 + 无维度用法） | region / city / store / seller / category / product / date + 无维度默认按天 | 每个配置维度至少 1 条（HP-012/021 覆盖无维度） |
| 天数档 | 昨日(1) / 近2日 / 近7日 / 近30日 / 显式绝对区间 | 每档至少 1 条 |
| 业务线 | retail / logistics / performance | 三线都有 |
| 指标数 | 单指标 24 条 / 多指标 3 条（HP-025/026/027） | 区分单多 |
| 难度 | easy 9 / medium 14 / hard 4 | 分级标注 |

**难度分级规则**（`difficulty` 的判定逻辑，扩充用例时沿用）：
- `easy`：单指标 + region/city 常规维度 + 相对/绝对日期无歧义词
- `medium`：分母型指标（aov/refund_rate/achieve_rate/ontime_rate）或 store/seller/category/product/date 维度或绝对日期
- `hard`：多指标组合、跨业务线、工具链、并行、对抗、越权

### 3.2 全类别分布

| 类别 | 数量 | 覆盖点 |
| --- | --- | --- |
| happy_path | 27 | 维度×指标×天数、单/多指标、三业务线 |

## 4. 怎么加载到 pytest（你自己写测试时用）

黄金集是**数据**，不含测试逻辑。加载示例（原理，不是替你写好的测试套件）：

```python
import json
import pytest

CASES = [json.loads(l) for l in open("tests/golden/golden_cases.jsonl", encoding="utf-8")]

@pytest.mark.parametrize("case", [c for c in CASES if c["category"] == "happy_path"],
                         ids=lambda c: c["id"])
def test_happy_path(chat, case):
    resp = chat(case["context"]["user_id"], case["query"])
    assert resp["answer_type"] == case["verdict"]["answer_type"]
    for frag in case["verdict"]["sql_must"]:
        assert frag in (resp.get("sql") or "")
    # rows_exact 比较：把 resp.rows 按首列转成 dict，再与冻结值比
    got = {str(r[0]): r[1] for r in resp.get("rows", [])}
    assert got == case["verdict"]["rows_exact"]
```

按标签选择回归集合：

```bash
pytest -q -k "HP"                      # 只跑正向
pytest -q -k "adversarial or anomaly"  # 只跑异常+对抗
```

## 5. 软断言 vs 硬断言（真实 LLM 的随机性怎么处理）

这是黄金集落地最重要的一条：

| 断言对象 | 类型 | 理由 |
| --- | --- | --- |
| `answer_type` / SQL 文本 / `rows_exact` / `forbidden_text` | **硬断言** | 一旦链路走通，编译与执行是确定性的（temperature=0） |
| `tools_must`（工具选择） | **软断言** | 真实 LLM 选工具有随机性；用成功率 `≥0.8`（5 次采样至少 4 次对） |
| `args_contract` 里的具体日期 | 硬断言（可选放宽） | 模型换算日期可能差一天；若只想验"格式合法"，用正则而非精确值 |

机制测试走白盒（`provider=whitebox_dispatcher`）：绕过 LLM 直接驱动 dispatcher，参数确定，全硬断言——这是"测机制"和"测模型"分开的关键。

## 6. 使用边界与已知约束

1. **多轮跨 turn 的 ctx**：`_TURN_CTX` 按 `turn_id` 隔离，当前 `chat_fc` 每请求新建 turn，所以"上一轮查、这一轮导"的上下文不跨请求。MT-004 标注此为已知边界；要测跨轮需把 ctx 挪到 `session_id`（未改造）。
2. **并行调用**：PA 用例允许模型分两轮完成，软断言；强制同轮需 `tool_choice` 或 prompt 强化。
3. **黄金值依赖数仓快照**：重建会覆盖冻结值。正式变更指标口径时，先评审再重建，并在 changelog 记录——否则测试会"跟着实现改预期"，失去守卫意义。
4. **JSONL 是主交付**：一行一例，便于参数化；YAML 供人读与 diff。两者由同一构建器产出，勿手工只改其一。
